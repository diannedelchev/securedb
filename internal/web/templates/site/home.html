WHY SECUREDB

Bank-grade guardrails, developer-grade speed.

Give every engineer, analyst and auditor exactly the database access they need — and a complete record of how they used it.

Policy-governed queries

Per-environment rules for row limits, timeouts, blocked keywords and WHERE-less writes. Unknown statements fail closed.

Automatic data masking

Cards, IBANs, national IDs, passwords and secrets come back masked by pattern rules — before they ever reach the browser.

Approvals & just-in-time access

Production writes require four-eyes approval, or a time-bound access window (15 minutes to 8 hours) that expires automatically.

Complete audit trail

Every query, login, approval and policy change is recorded with actor, origin IP and full statement — searchable by your auditors.

Credentials that never leave the server

Database passwords are AES-256-GCM encrypted at rest and decrypted just-in-time inside the connector layer — never sent to a client.

One gateway, every engine

PostgreSQL, MySQL/MariaDB and Microsoft SQL Server behind a single connector interface — with optional SSH tunnels to reach them.

HOW IT WORKS

From zero to governed access in three steps.

SECURITY MODEL

Built like the systems it protects.

SecureDB is a control plane between people and production data. Its own security posture is engineered to the same standard it enforces.

  • AES-256-GCM encryption for stored database and SSH credentials; bcrypt for user passwords.
  • Hardened sessions — opaque 256-bit tokens stored hashed, HttpOnly cookies, idle and absolute expiry, CSRF protection on every state change.
  • Four-eyes principle — no self-approval on production writes or access windows; approvals execute once and expire in 24 hours.
  • Read-only enforcement at the connector level, backed by database-native read-only transaction modes.
  • Role-based access for admins, DBAs, developers, QA, analysts and auditors — each sees only what their role permits.
