FEATURES

Everything you need to govern database access.

A full workspace for the people who query, and full control for the people who answer for it. Here is what ships in the box.

THE WORKSPACE

A serious SQL client, in the browser.

Everything your team expects from a desktop client — editor, explorer, history — available from any desktop browser or iPad with nothing to install.

SQL Editor

A full-bleed IDE with a schema tree, tabs, Run (⌘⏎), Explain and Stop. Policy-driven LIMIT and READ-ONLY chips show the rules in force before you run. Results arrive in a line-numbered grid with masking badges, copyable rows, saved queries and a history rail.

Database Explorer

A three-pane browser: a filterable object tree, tabbed Columns / Constraints / Indexes grids, and an inspector showing object statistics and your effective permissions on each table.

Query History

A day-grouped timeline of everything you ran, with risk badges, blocked-query callouts, expandable execution detail, one-click replay and copy.

Operations Dashboard

KPI cards, a 24-hour query-volume histogram, slow queries, recent connections, environment status, pending access requests and a live activity timeline.

Connection management

A card grid with environment, read-only and tag chips, last-used times and one-click test. One connection covers every database on the server — switch databases in the editor and explorer without re-registering anything.

SSH tunnels built in

Reach databases behind a bastion or jump host with per-connection SSH tunnels — password or private-key auth, encrypted at rest, with optional host-key fingerprint pinning.

GOVERNANCE

Guardrails that work at query time.

Every statement passes through the policy engine before it touches a target database: classify → check → block, approve or execute → mask → record.

Per-environment policy engine

Row caps, statement timeouts, blocked keywords, WHERE-less write rules and multi-statement limits — configured separately for development, staging and production. Statements the engine cannot classify are blocked, not waved through.

Column-pattern data masking

Masking rules match column names by pattern and rewrite values server-side. Masked columns are flagged in the result grid, so users always know what they are not seeing.

One-time query approvals

Production writes create an approval request carrying the exact SQL, target database, an automated risk analysis and a timeline. A different admin or DBA must approve (four-eyes); the requester then gets one run within 24 hours — against exactly the SQL and database that were reviewed.

Just-in-time access windows

For planned maintenance, request a time-bound write window (15 minutes to 8 hours). Approved windows let production writes run without per-query approval — tagged in the audit log, revocable at any time, and never exempt from hard guardrails.

OVERSIGHT

Answers for your auditors, before they ask.

Audit logs

Every security-sensitive action — logins, queries, blocks, approvals, grants, policy changes — recorded with actor, IP address, user agent, full statement text and severity. Readable by auditors, DBAs and admins; secrets are never logged.

Security Center

A live posture score computed from your actual policy configuration, a threat timeline, blocked-queries chart and risk indicators — plus the per-environment policy and masking-rule editors, in one place.

Users & roles

Six built-in roles — admin, DBA, developer, QA, analyst, auditor — with per-user role assignment, enable/disable, and permission summaries at a glance. Admin-only.

Approval Requests console

A master-detail review queue for both approval types — one-time query approvals with a risk meter, and access-window requests — with decision timelines and a pending-count badge in the navigation.

PLATFORM

Simple to run, hard to misuse.

Multi-engine connectors

PostgreSQL and MySQL/MariaDB supported today, Microsoft SQL Server on the roadmap — all behind one connector interface, so guardrails behave identically on every engine.

Server-side secrets

Database and SSH credentials are AES-256-GCM encrypted in the application database and decrypted just-in-time inside the connector layer. They are never rendered into a template or sent to a browser.

Hardened by default

Bcrypt password hashing, hashed session tokens, HttpOnly cookies with idle and absolute expiry, CSRF verification on every state-changing request, and strict security headers on every response.

Single-binary deployment

Templates, assets and migrations are embedded — deploy one self-contained binary or the provided Docker image, point it at a PostgreSQL server, and you are running.
